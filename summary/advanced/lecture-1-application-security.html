Lecture 1 — Application Security

Application security : the set of measures and practices that protect software applications from threats and vulnerabilities throughout their life cycle. It is a specific subset of cybersecurity focused on securing software itself.

AreaWhat it protectsTypical measures
Network securityTraffic and connections between systemsFirewalls, segmentation, IDS, VPNs
Infrastructure / cloudServers, containers, VMs, cloud accountsHardening, patching, IAM, configuration baselines
Physical securityBuildings, data centers, devicesBadges, locks, cameras
Application securityThe software: design, code, dependencies, runtime behaviourThreat modeling, secure coding, code review, SAST/DAST, dependency scanning, monitoring

Shift-left : moving security activities earlier in the life cycle so feedback arrives while the code is still fresh.

Security objectives

Confidentiality : data is accessible only to authorized parties.

Integrity : data cannot be modified by unauthorized parties.

Availability : the application and its data are accessible when legitimate users need them.

Authentication : verifying a user, device or system is who it claims to be.

Authorization : deciding what an already-authenticated identity may do or see.

Accountability : trustworthy evidence of who did what and when, so actions can be reconstructed and not denied.

ObjectiveCore questionMechanismsTypical failures
ConfidentialityCan an unauthorized party read it?Encryption, access control, data classificationMissing access control, unencrypted data, verbose errors, IDOR
IntegrityCan it be changed without authorization?Input validation, digital signatures, audit trailsNo input validation, no signatures, SQL injection
AvailabilityCan users reach it when needed?Rate limiting, redundancy, capacity planningDoS, resource exhaustion, unpatched crashes
AuthenticationWho are you?Passwords, MFA, certificatesWeak/reused passwords, no MFA, predictable tokens
AuthorizationWhat may you do?RBAC, policy enginesMissing object-level checks, hidden buttons instead of server checks, broad roles
AccountabilityCan we prove who did what, when?Audit logs, timestamps, correlation IDsMissing logs, no user/time, tamperable logs
Example: a support agent who changes an account ID in the URL and sees every company's invoices — authenticated correctly, authorized wrongly.

Threat modeling

Threat modeling : a systematic process to identify, understand, prioritize and mitigate threats before and throughout implementation — proactive instead of reactive.

Vulnerability : a weakness. Threat : a potential action/event that could exploit it. Risk : the potential consequences in context.

Q/ What are the three fundamental threat-modeling questions ?

  1. What are we building? Components, users, assets, data flows, dependencies, trust boundaries.
  2. What can go wrong? Threats to C, I, A, authentication, authorization, accountability.
  3. What are we going to do about it? Preventive, detective, corrective controls; manage residual risk.

Data Flow Diagram (DFD) : a structured picture of how information moves through the system, used to expose attack-relevant parts.

Q/ What are the elements of a security DFD ?

  1. External entities (users, external apps, third parties).
  2. Processes (components that receive/transform/validate data).
  3. Data stores (databases, files, caches, queues, backups).
  4. Data flows (exchanges between them).
  5. Trust boundaries (the fifth, most important concept).

Trust boundary : a logical line where the level of trust, privilege or control changes (not necessarily a network boundary).

Mobile app example: the device is untrusted — the server must independently authenticate, authorize and validate; never rely only on client-side checks.

STRIDE : Microsoft's threat-modeling framework of six categories.

STRIDEDefinitionProperty violatedControls
SpoofingPretending to be another user/device/serviceAuthenticationMFA, credential & session management, token validation
TamperingUnauthorized modification of data, requests, config or softwareIntegrityEncrypted channels, server-side validation, signatures, DB constraints
RepudiationDenying an action with no trustworthy evidenceAccountability / non-repudiationSecure audit logs, timestamps, transaction IDs, tamper-resistant logs
Information disclosureData reaches unauthorized partiesConfidentialityEncryption, access control, least privilege, data minimization, safe errors
Denial of serviceUsers can't access the service / it degradesAvailabilityRate limiting, quotas, size limits, load balancing, DDoS protection
Elevation of privilegeGaining permissions beyond those assignedAuthorizationServer-side authz, RBAC/ABAC, least privilege, object-level checks

Risk score : Likelihood × Impact, each rated High 3 · Medium 2 · Low 1 → score 1–9.

LevelLikelihoodImpact
High (3)Little skill/access; tools readily availableMany users, big loss, sensitive data, safety
Medium (2)Some skill, privileged access or conditionsOne user or limited group, moderate damage
Low (1)Advanced skill, rare access, many conditionsMinor, temporary, reversible
Don't confuse the dimensions: a whole-database breach has high impact but isn't automatically likely. Don't rate everything High; justify each rating.

Q/ QuickBite worked example — what are the trust boundaries and top threats ?

  • TB1 Internet → QuickBite cloud (all client devices untrusted). TB2 QuickBite → payment provider (authenticate both ways). TB3 app tier → data tier.
  • Top five: I2 IDOR on /orders/5521→5522 (9), S1 account takeover by credential stuffing (9), T1 price tampering (9), E1 customer calls restaurant endpoints (6), D2 API/promo flooding at peak (6).
  • Tie-break order: personal safety → users affected → cost.

Secure coding practices

PracticeRule
Input validationNever trust input; check type, length, format, range; prefer allow-lists
Parameterized queriesKeep SQL code separate from data (stops ' OR '1'='1)
Output encodingEncode special characters so the browser shows text, not code (XSS)
Password storageSalted, slow hash (bcrypt, Argon2); never MD5/SHA-1
Authentication & sessionsMFA, lockout/slow-down, random session IDs, HttpOnly/Secure/SameSite, idle expiry
Authorization & least privilegeCheck permission on every request; minimum rights (DB account can't DROP TABLE)
Secrets managementNo hard-coded keys; load from env or a secrets manager; never commit to Git
Error handling & loggingGeneric messages to users, details in protected logs, no sensitive data in logs
EncryptionHTTPS/TLS in transit, encryption at rest; never invent your own crypto
Secure defaults / fail-safeSecure out of the box; on failure fail closed (deny)
Code review & testingPeer review, SAST (Bandit, SonarQube), DAST, penetration testing
CSRF protectionStop a logged-in browser being tricked into unwanted requests (tokens, SameSite)
Fail-safe example: if check_permission throws, set allowed = False, never True.
